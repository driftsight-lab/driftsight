## 0. 공통 규칙

### 0.1 시드

- 기본 시드 `42`. 반복 실험은 3회 이상 `[42, 43, 44]`(기획서 7.4 과제 A), 주입 실험은 시나리오당 10회 `[42..51]`(기획서 7.3(6))
- 고정 대상: `random`, `numpy`, `torch`(+ `torch.backends.cudnn.deterministic=True`), 데이터 분할, 표본 추출, 트래픽 생성기 질문 순서
- LLM 호출은 `temperature=0`으로 하되 완전히 결정적이지 않으므로, 응답 원문을 캐시해 재분석 시 재사용한다

### 0.2 데이터 분할

| 데이터 | 분할 | 규칙 |
| --- | --- | --- |
| RAGTruth | 공식 train / test + train에서 검증(dev) 10% 분리 | `source_id` 단위로 분리한다. 같은 근거 문서에 대한 응답 6개가 train·dev에 갈라지면 누출되기 때문 |

test·보고용 분할은 하이퍼파라미터·프롬프트 조정에 쓰지 않는다. 위반한 결과는 log.md에 `contaminated`로 표시하고 보고에서 뺀다.

## 과제 A. 경량 환각 탐지 모델

- **질문**: 정확도 손실을 최소화하면서 CPU 지연·모델 크기를 얼마나 줄일 수 있는가?
- **관련 ADR**: ADR-023 (ONNX Runtime CPU 서빙·INT8 양자화), ADR-027 (자체 미세조정 인코더 + LettuceDetect 기준선), ADR-028 (과제 A 개선 축: 추론 효율)
- **데이터**: RAGTruth train(학습) / dev(학습률·최대 길이 선택) / test(최종 1회 보고)

**비교 대상**

| 구분 | 모델 |
| --- | --- |
| 기준선 | LettuceDetect (PyTorch FP32) |
| 자체 모델 | ModernBERT·DeBERTa-v3 크기별 미세조정 |
| 서빙 형식 | 각 모델의 PyTorch FP32 / ONNX FP32 / ONNX INT8(동적 양자화) |

**학습 순서** (우선순위 순)

1. ModernBERT-base: 기준선(LettuceDetect base)과 같은 백본이라 비교가 가장 공정하다
2. 더 작은 백본(DeBERTa-v3 small 계열 등): 효율 곡선의 "작은 쪽" 점
3. 시간이 남으면 나머지 크기

**입력·라벨 규칙** (확정)

- 입력: `[문맥] [질문] [답변]`을 이어 붙인다. 최대 길이를 넘으면 문맥 앞쪽부터 잘라 답변은 항상 남긴다.
- 라벨: 답변 토큰에만 0(근거 있음)/1(환각)을 붙인다. 답변 토큰 중 RAGTruth 환각 구간(문자 오프셋)과 한 글자라도 겹치는 토큰은 1. 문맥·질문·특수 토큰은 손실 계산에서 제외한다(라벨 −100).
- `implicit_true` 구간: **환각에 포함(label=1)** — LettuceDetect 전처리 코드 기준 준수. LettuceDetect는 `implicit_true` 여부와 관계없이 모든 라벨 구간을 환각으로 쓴다. 기준선과 동일한 규칙을 써야 F1 비교가 유효하다(E-7-A 확정: LettuceDetect와 동일).
- `quality` 플래그: **LettuceDetect 전처리 코드와 동일하게 처리** — LettuceDetect는 `quality`를 보지 않으므로 `incorrect_refusal`·`truncated` 응답도 모두 포함한다(E-7-B 결정 C).
- **`score` 방향**: 답변 토큰들의 환각 확률 중 최댓값. **높을수록 환각 의심**↑. [interfaces.md](../specs/interfaces.md) `Detector.name` 규칙(`{모델명}-{서빙형식}`)으로 `evaluator_key`를 부여한다([erd.md](../specs/erd.md) 1장 점수 방향 원칙, ADR-027).
- `spans`: 확률이 0.5 이상인 연속 토큰을 묶은 문자 구간.

**수치 표기 규칙**: 기준선은 논문·모델 카드 공식 수치와 우리 평가 코드로 재현한 수치를 따로 적는다. 비교 그래프·결론에는 재현 수치만 쓴다(같은 분할·같은 코드).

**지표**

| 지표 | 정의 |
| --- | --- |
| 응답 단위 F1 | 응답에 환각 구간이 하나라도 있으면 양성. micro F1 |
| 토큰 단위 F1 | 답변의 각 단어가 환각 구간에 속하는지를 양성으로 본 F1 (전체 test 합산, micro). 공백 기준 단어 단위로 통일해 계산 |
| 문자 겹침 구간 F1 | LettuceDetect 논문 수치와 비교하기 위한 보조 지표 |
| 모델 크기 | 파라미터 수, 디스크 크기(MB) |
| 처리량 | 초당 처리 응답 수 (배치 크기 명시) |
| CPU p50/p95 지연 | EC2 t3.large(2 vCPU), 예열 50회 후 응답 1건 기준 500회 측정 |
| F1 하락폭 | ONNX INT8 적용 후 F1 − 적용 전 F1 |

**토큰 단위 F1의 단어화·라벨 변환 규칙** (정답과 예측에 동일하게 적용)

1. 답변 텍스트를 공백 기준으로 나눠 단어 목록을 만든다. 문장부호는 붙어 있는 단어에 포함한다.
2. 각 단어의 문자 범위 `[시작, 끝)`을 기록한다.
3. 정답 라벨: 단어 범위가 RAGTruth 환각 구간과 한 글자라도 겹치면 1, 아니면 0.
4. 예측 라벨: 단어 범위가 모델이 낸 `spans`와 한 글자라도 겹치면 1.
5. test 전체의 단어를 모아 TP·FP·FN을 세서 F1을 한 번 계산한다(micro).

**하위 분석**: RAGTruth 과제 유형별(QA / Summary / Data2txt), 입력 길이 구간별

**산출물**: 정확도–효율 곡선 (x: CPU p95 지연 또는 크기, y: 응답 단위 F1)

**추가 평가**: 자체 RAG 서비스의 주입 실험 응답으로 RAGTruth 밖 분포에서의 성능 확인 (정답 = 2단계 전수 채점 기준, 한계 명시)

## 과제 B-1. 채점자 신뢰도 검증

*(모델 파트 담당, SP2 필수)*

- **데이터**: MT-Bench human judgments (`human` split: 사람 쌍 비교 약 3,300건, `gpt4_pair`: GPT-4 판정)
- **채점자**: 2단계와 같은 Claude 중형 모델 + 같은 채점 프롬프트 형식
- **방법**: 같은 (질문, 모델 A, 모델 B, 턴) 쌍을 채점자에게 A·B 순서를 바꿔 2번 판정시킴

| 지표 | 정의 |
| --- | --- |
| 일치율(무승부 포함) | 채점자 판정 = 사람 판정인 비율, 판정값 ∈ {A 승, B 승, 무승부} |
| 일치율(무승부 제외) | 사람 판정이 무승부가 아닌 쌍만 대상 (Zheng et al. 2023 방식) |
| Cohen's kappa | 3개 클래스 기준, 우연 일치 보정 |
| 순서 교환 일관성 | 순서를 바꾼 2회 판정에서 같은 승자를 고른 비율 |
| 길이 편향 | 답변 길이와 판정의 상관계수 r. 보조로 더 긴 답변이 이긴 비율을 채점자·사람 각각 계산해 비교 |
| 사람 간 일치율(기준) | 같은 쌍에 사람 평가자가 여럿인 경우 그들끼리의 일치율. 채점자–사람 일치율을 이 값과 비교해 해석 |
| GPT-4 대비 | `gpt4_pair`와 우리 채점자의 일치율 (참고) |
- **보정 실험**: 편향이 보이면 "순서 교환 2회 평균" 판정을 적용해 위 지표를 다시 측정
- **교차 검증**: 운영 2단계 채점 결과 중 100~200건을 다른 제공자 채점자로 재채점 → 일치율·kappa 보고(ADR-015)
- **한계**: MT-Bench는 영어 일반 대화의 선호 비교이고, 운영 2단계는 근거 문서 대비 환각 판정이다. B-1 결과는 "채점자가 사람 판단과 대체로 맞는가"의 근거이며, 환각 판정 정확도 자체는 B-2에서 RAGTruth 사람 라벨로 확인한다.
- **산출물**: 채점자 신뢰도 화면 데이터 (일치율, kappa, 혼동 행렬, 순서·길이 편향, 불일치 사례 목록). api.md 8.2 `GET /api/v1/experiments/judge-reliability` 응답 구조와 일치해야 한다.

## 과제 B-2. 2단 라우팅

*(구현·실험: 서비스 파트 / 분석·보정·화면: 모델 파트)*

- **라우팅 규칙**: stage 1 `score ≥ τ` → 2단계(`routed_reason=threshold`), 나머지 중 비율 `r`을 무작위 표본으로 2단계(`routed_reason=sample`). erd.md 1장 점수 방향 원칙 적용 — `score`는 **높을수록 환각 의심**↑.
- **격자**: τ ∈ {0.3, 0.5, 0.7, …} × r ∈ {0%, 5%, 10%}
- **데이터 두 가지**
    1. RAGTruth test (사람 라벨 있음) → 정확도 유지율 계산
    2. 자체 RAG 서비스 응답 (MS MARCO 질문) → 실제 API 비용·누락률 계산. 
        - 정답 대용 = 같은 응답을 2단계로 전수 채점한 결과
        - 한계: 정답 대용이 LLM 채점 기반이다.

| 지표 | 정의 |
| --- | --- |
| 2단계 호출 비율 | (threshold + sample) 건수 / 전체 |
| 비용 절감률 | 1 − (2단 구조 총비용 / LLM 단독 전수 채점 총비용). 1단계 서버 비용 포함 여부 명시 |
| 정확도 유지율 | 2단 구조 최종 판정 F1 / LLM 단독 전수 채점 F1 (RAGTruth 사람 라벨 기준) |
| 누락률 | 전수 채점에서 환각인 응답 중 2단계로 전달되지 않은 비율 |
| 누락률 추정 오차 | 무작위 표본(r)만으로 추정한 누락률 − 실제 누락률 |
- **점수 보정(Calibration)**: dev에서 온도 스케일링 또는 isotonic 회귀로 1단계 점수를 확률에 맞춘 뒤 τ의 의미를 해석. 보정 전후 ECE 보고
- **산출물**: (비용 절감률, 정확도 유지율, 누락률) 곡선 → 라우팅 정책 화면(api.md 6장), policies.md τ·r 기본값 근거

## 과제 C. 품질 저하 탐지

- **질문**: 3방식(고정 임계값, KS 검정, 임베딩 거리)과 시간 창 크기에 따라 탐지 지연과 오탐률이 어떻게 상충하는가?
- **관련 ADR**: ADR-029 (드리프트 탐지 3방식 교체 가능 구현체)
- **데이터**: 주입 실험 트래픽(기획서 7.3(6), 0.5 rps, 90분, 30분 시점 주입)
    - 시나리오 5종(`SCN-001`~`SCN-005`) × 10회 (시드 42~51). injection-scenarios.md 8장 참조
    - 대조 실행(`SCN-000`): 주입 없는 정상 실행 10회. 임계값 보정과 오탐 측정용
- **변수**: 방식 3 × 시간 창 {5분, 15분, N건(≈150건, 0.5 rps×5분)} × 민감도 설정(분위수 또는 α 3단계)

**절차**

1. 임계값 보정: 대조 실행 중 5회의 정상 창 분포로 각 방식·창 크기의 임계값을 정한다(ADR-029 결정 3)
2. 평가: 나머지 대조 실행 5회 + 시나리오 실행 50회에 고정된 임계값을 적용
3. 저하 확인(전제 조건): 시나리오마다 주입 전·후의 2단계 전수 채점 환각 비율을 비교해 실제로 품질이 떨어졌는지 먼저 확인한다. 저하가 확인되지 않은 시나리오는 탐지율 계산에서 제외하고 별도 보고한다.
    - 판정 기준 (제안): 10회 실행을 합쳐 주입 전 30분과 주입 후 60분의 환각 비율을 두 비율 차이 검정(단측, α=0.05)으로 비교하고, 동시에 환각 비율이 **2%p 이상** 증가했을 때 "저하 확인"으로 본다. 표본이 커서 아주 작은 차이도 유의하게 나오는 것을 막기 위해 효과 크기 조건을 함께 둔다.
    - 주의: 드리프트 판정과 품질 저하는 다르다. 임베딩 분포가 바뀌어도 품질은 그대로이거나 좋아질 수 있다. "드리프트 탐지 성공"은 저하가 확인된 실행에서만 센다.

| 지표 | 정의 |
| --- | --- |
| 탐지율 | 시나리오 실행 중 주입 시점 이후 한 번이라도 드리프트로 판정된 실행 비율 |
| 탐지 지연 | 첫 드리프트 판정 창의 끝 시각 − 주입 시각(분). erd.md `incidents.detected_at` − `injection_events.applied_at` |
| 오탐 횟수 | 정상 구간에서 드리프트로 판정된 창 수. 정상 1시간당 횟수로도 환산 |
| 저하 시작 추정 오차 | `estimated_start_at` − 실제 주입 시각 |
| 판정 시간 | `DriftDetector.judge()` 1회 CPU 시간 (interfaces.md 7.3 성능 제약: 100ms 이내) |
- **산출물**: 방식별 (탐지 지연, 오탐 횟수) 곡선, 민감도 설정을 바꿔 가며 그린 상충 관계 그래프

## 과제 D. 원인 변경 탐지 평가

*(구현: 서비스 파트 / 평가 설계·채점: 모델 파트)*

- **데이터**: 과제 C와 같은 시나리오 실행. 디코이 변경 포함 조건과 미포함 조건을 모두 실행(injection-scenarios.md 5장 디코이 규칙)
- **정답**: 시나리오 YAML의 주입 변경 = `version_changes`에서 `source=injection`이고 `is_decoy=false`인 행(injection-scenarios.md 3.2 정답 라벨 정의)
- **비교**: 에이전트 vs 규칙 기반 기준선(저하 시작 직전의 변경을 지목)

| 지표 | 정의 |
| --- | --- |
| Top-1 정확도 | 에이전트가 1순위로 고른 변경 = 정답인 비율. `incidents.top1_version_change_id` = 정답 `version_change_id` |
| Top-3 정확도 | 상위 3개 후보 안에 정답이 있는 비율. `incidents.agent_result` 배열에서 계산 |
| 근거 정확성 | 결론에 인용한 근거가 실제 도구 호출 결과에 있고 정답 변경과 품질 하락을 연결하는지. 아래 체크리스트로 독립 판정 후 합의 |
| 디코이 오지목률 | 디코이 변경을 1순위로 고른 비율 |
| 조사 비용 | 도구 호출 수, 토큰 수, API 비용, 소요 시간. `agent_steps` 집계 |
| 상한 도달 비율 | MAX_STEPS=12·TOKEN_BUDGET=60,000에 도달해 규칙 기반 대체 결과를 낸 비율(`agent_fallback=true`) |

판정 자동화: 에이전트 출력은 구조화된 JSON(원인 후보 순위 + 신뢰도 + 근거)이므로 Top-k는 `version_change_id` 비교로 자동 계산한다(erd.md 3.2 쿼리 예시).

**근거 정확성 체크리스트** (제안, 1순위 후보의 근거에 적용)

| # | 항목 | 판정 |
| --- | --- | --- |
| 1 | 사실성: 인용한 수치·시각·버전이 에이전트의 `agent_steps` 도구 호출 기록에 실제로 있다 | 예/아니오 |
| 2 | 출처 일치: 근거마다 어떤 도구 호출 결과인지 연결되어 있다 | 예/아니오 |
| 3 | 시점 연결: 변경 시각과 저하 시작 시각의 관계를 근거로 제시한다 | 예/아니오 |
| 4 | 전후 비교: 변경 전·후 품질 차이(`compare_versions` 등)를 근거로 제시한다 | 예/아니오 |
| 5 | 대안 배제: 다른 후보(특히 디코이)가 원인이 아닌 이유를 하나 이상 제시한다 | 예/아니오 |

근거 정확성 = 1·2번이 모두 "예"이고 3·4번 중 하나 이상 "예"인 비율. 5번은 따로 보고한다. 두 사람의 판정이 다르면 논의 후 합의하고, 합의 전 불일치 건수와 Cohen's kappa를 기록한다.

## 참고. 버전별 A/B 비교 화면의 통계

*(모델 파트 화면, SP3 필수, api.md 4.4 참조)*

기획서 4.3·5장: 두 버전을 같은 기간·같은 질문 집합으로 비교하고 표본 수와 통계적 유의성을 표시한다.

| 지표 | 같은 질문을 두 버전에 모두 보낸 경우 (대응 표본) | 질문이 서로 다른 경우 (독립 표본) |
| --- | --- | --- |
| 평균 품질 점수, 평균 지연, 요청당 비용 | Wilcoxon 부호 순위 검정 | Mann–Whitney U 검정 |
| 환각 비율 | McNemar 검정 | 두 비율 차이 검정 (카이제곱 또는 Fisher 정확 검정) |
- 기획서 4.3 "같은 기간·같은 질문 집합" 비교는 대응 표본이 기본이다. 운영 트래픽처럼 질문이 겹치지 않으면 독립 표본 검정을 쓴다.
- 여러 지표를 한 화면에서 동시에 검정하므로 다중 비교 보정(예: Holm) 적용 여부를 함께 정한다.
- 표본 수가 기준 미만이면 "유의성 판단 불가"로 표시한다.
